# FP8 GEMM: the composed reference WGSL, line by line, against `gemmFp8.ts`

three-dlss-nr ports OpenDLSS-NR by maan (MIT, pinned at `9d08f41`). The spec for `createGemmFp8` is the reference's
**composed** production kernel, not its readable base kernel. The composed kernel is
`variantCode({ output, residual: 'e4', batched, tile128: true })` from
`reference/OpenDLSS-NR/ports/browser-webgpu/src/matmul/variants.js`, with the overrides graph.js `Graph.gemm` sets.
This audit maps every line of that text to the TSL. It is a second line of evidence, independent of the executable
ones:

- `gemmFp8.gpu.test.ts` checks the TSL against `oracleGemmFp8` on every graph role, everywhere (D3D12/FXC locally).
- `test/browser/run-fp8-gemm-chrome.mjs` runs the reference itself in Chrome on real f16 hardware (RTX 3060 Ti, D3D12
  - DXC) on the same roles and inputs. It equals `oracleGemmFp8` bit for bit on all 23 roles and the 7 CI cases, and
    its GPU-built SiLU table equals ours for every non-NaN half.
- Reference parity in vitest (`it.for` + `context.skip`) runs wherever the reference has trustworthy `shader-f16`.
  That excludes this machine's Dawn, and it excludes lavapipe, which folds `f32(f16(x))`; see
  `src/README-internals.md`.

Line numbers below are in the `e4` non-batched variant. To dump it:

```sh
node -e "import('./reference/OpenDLSS-NR/ports/browser-webgpu/src/matmul/variants.js').then(m => console.log(m.variantCode({ output: 'e4', residual: 'e4', batched: false, tile128: true })))"
```

The `half`, `dual` and batched variants differ only where noted in the last sections. Their hashes are pinned by
`test/reference/composedWgsl.test.ts`.

## Flags the graph sets (graph.js:59-111)

`16` (swizzled input, always), `32` (quantize, unless the output is half-only), `4` (SiLU), `2|8` (residual + scale),
`262144` (residual is E4), `131072` (broadcast), and partition `1024` (none), `8192`, `16384` or `32768` (spans
1024 / 512 / 256). Flags `1, 64, 128, 256, 512, 2048, 4096, 65536` are never set. Every branch on them is dead, and
the TSL has no counterpart for those branches. JS-time constants replace all flags and overrides (`spec`).

## Variant differences

- **dual** (`rawHalfOutputMatmulCode`): `raw_values: array<f16>` at binding 7, and `raw_values[output_index] = f16(value)`
  per output inside the row/column guard. Ours: `nr_outputHalf` words `packHalfPair(f16Bits(v0), f16Bits(v1))` and
  `(v2, v3)` at `index >> 1`, the same bytes. Each invocation owns whole words because `n % 16 == 0` and the column
  base is a multiple of 4.
- **half** (`halfOutputMatmulCode`): the workgroup is `(16, 8)` with 4 rows x 2 columns per invocation (only the thread
  mapping), products `vec4<f16>(a0, a0, a1, a1) * (b0, b1, b0, b1)` (the same products), and
  `output_values: array<f16>[index] = f16(select(value, fp8_domain(value), flag 32))`. Flag 32 is never set for half,
  so this is `f16(value)`, exact. Ours: the e4 mapping (2 x 4) with two half words per row.
- **batched** (`batchedMatmulCode`): `column_groups = ceil(N / 32)`, `batch = group.x / column_groups`,
  `column_group = group.x % column_groups`; output index `+ batch * N`; weight offset `+ batch * K * WMC`; input stride
  `LAYOUT_INPUT_MATRIX_CHANNELS`, plus `batch * K` unless broadcast. Ours: the same, emitted only when `batches > 1`.
  graph.js also selects the batched text when `input.channels != k` with one batch. Ours handles any input stride
  the same way, because the stride is a baked constant.

## Deliberate differences (none visible in valid outputs)

1. **Guards on folded row tiles.** With `rows % 32 == 0` the reference folds its row guard away
   (`MATMUL_ROWS % 32u == 0u || row < MATMUL_ROWS`). The half-variant and dual raw-half stores keep only that guard.
   When the dispatch is folded (more than 65535 row tiles) and `65535 * z` exceeds the row tiles, the extra
   workgroups store half outputs past the tensor. WebGPU's robust access then clamps or discards those stores, so
   they can land on the last element. This first happens at a 1920x1152 field (2,211,840 rows, 69120 row tiles) in
   level-0 qkv and dual GEMMs. Our kernel guards rows whenever a tile can be partial or out of range.
2. **Workgroup memory** is `f32` / `i32` (18 KiB with padding) instead of `f16` (8.7 KiB), and B is k-major with one extra slot per eight columns.
   This changes layout only.
3. **Operands are not scaled by 4.** The reference relies on `|w| <= 9` (model.js) for exact half products. Our f32
   products are exact for any E4 weight, so the results differ only for a weight the reference itself refuses to load.

## Proposed shared-memory padding (#7)

This independent implementation isolates the addressing proposal discovered in
[PR #4](https://github.com/bhouston/three-dlss-nr/pull/4), head
`458384d776c98e0c75bea855319561fc50b110f6`, for
[issue #7](https://github.com/bhouston/three-dlss-nr/issues/7). It changes physical shared-memory addresses while
retaining logical operands, reductions, global addressing, partial-tile guards, formats, and rounding.

A values and exponents use `A[row * 9 + q]`; B values and exponents use
`B[q * 36 + column + floor(column / 8)]`. Every logical operand has a unique physical data slot; the extra
slots are not consumed. Four 288-element vec4 arrays occupy 18 KiB, within the actual TSL network requirement
of 24 KiB (`NR_MIN_WORKGROUP_STORAGE = 24576`). The reference backend separately requires 32 KiB.

Each producer has `t = local_index + 128 * j` (`j = 0, 1`), `q = t % 8`, and `outer = floor(t / 8)`:
`outer` is A's row and B's column. Consumers use row `2 * local.y + r` (`r = 0, 1`) and column
`4 * local.x + c` (`c = 0..3`) with the same slot formulas. Enumerating all 256 producers and 8192 consumer
pairs confirms unique producer addresses and matching operands. A slot 8 per nine-slot row is unused;
B slots 8, 17, 26 and 35 per 36-slot quad are unused. This common mapping applies to every role, batch,
broadcast, folded row group and partial tile; their global addresses, guards and zero fills are unchanged.
Generated WGSL declares exactly four arrays of 288 16-byte vec4 elements: `4 * 288 * 16 = 18432` bytes.

This adapts the pinned upstream `matmul/padded.js` idea to TSL's 2-row / 4-column invocation mapping.
The proposal needs independent idle-GPU measurements before adoption: bank behavior and occupancy are
hardware-dependent. The maintainer was using the local GPU during evaluation, so all local timing observations
were discarded as performance evidence. Local tests validate correctness only; no speedup or regression claim
is made. Keep the PR in draft until another machine verifies kernel and full-network parity and demonstrates
that padding does not introduce a material performance regression. See `gemm.bench.gpu.test.ts` for the existing
synthetic GEMM timing harness, and the shared validation handoff for benchmark and merge gates.
